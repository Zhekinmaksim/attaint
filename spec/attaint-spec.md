# Attaint: dependency update consensus gate

This specification describes the repository implementation. The ABI in
[`contracts/attaint.py`](../contracts/attaint.py) is authoritative. The Bradbury
deployment artifact is
`contracts/attaint.bradbury.py`, generated by `scripts/compile_contract.py`. The
compiler uses `python-minifier==3.1.1` from `requirements-dev.txt` to remove
comments/docstrings and shorten internal names and whitespace for the RPC
transaction gas cap. It preserves the public ABI, storage fields, annotations
and prompt strings and checks public method/argument names. Run the full offline
suite against both the readable source and generated artifact. Deployment
addresses and live results belong to verified run artifacts, not this document.

## Object and trust model

The object is one npm package moving from version A to version B. A client builds
an `attaint/1` envelope from registry metadata and checksum-verified tarballs,
then submits bounded evidence to an Intelligent Contract on GenLayer. Consensus
judges the update under an immutable consumer policy. The consumer reads the
result through `gate()` and uses it to block or permit CI.

A checksum pins bytes, not truth. The contract checks the submitted envelope's
format, canonical hash, update identity and pin structure. It does not download
multi-megabyte tarballs or verify that the client extracted file content faithfully.
For level 1, a strict-equality consensus round fetches npm version manifests and
compares package/version identity, declared integrity, licence, publisher,
maintainers, hooks, dependency changes and package purpose when supplied. A mismatch or failed fetch produces
`INCONCLUSIVE`. This metadata check does not authenticate the file excerpts.
Public source URLs, rebuilding and comparison are part of verification. Registry metadata and release
content can be wrong or hostile.

A verdict concerns the selected classes and supplied evidence. Bounded excerpts
cannot establish the safety of a whole package, detect every hidden network call,
or replace vulnerability scanning and code review.

## Policy and verdict vocabulary

`register_policy(allowed_licenses, blocking, min_rounds, min_level,
challenge_bond)` registers a policy and records its hash. Lists are canonicalised;
class names must come from the six supported risk classes. A policy cannot be
edited. Changing consumer requirements requires a new policy ID and hash.
Funding a policy changes its pool, not its rules.

The six classes are `LICENSE_SHIFT`, `MAINTAINER_SHIFT`, `INSTALL_HOOK`,
`OPAQUE`, `EGRESS` and `DEP_ADDED`. Their judgment questions and evidence limits
are in [`classes.md`](classes.md). Deterministic candidate extraction does not
assign these verdicts. All class questions use harmful polarity: `found=true`
means a risk introduced by the update. Explained opaque content and a dependency
with an evidenced role are ordinary, not positive risk findings. Install judgments
concern new or changed behaviour; unchanged ordinary commands are not new risks.
The prompt treats a complete empty candidate set as not found within that class
extraction scope and incomplete coverage as inconclusive. Missing origin evidence
or an ambiguous new install command without its body remains inconclusive.

`min_rounds` counts completed per-class judgments, not validator votes or repeated
independent runs of one class. One pass judges each readable blocking class once.
A threshold greater than that count yields `INCONCLUSIVE`. `min_level` is the
weakest acceptable evidence level: 1 requires registry-tarball evidence; 2 also
permits lockfile evidence when every required class is supported.

## Evidence protocol

The canonical envelope retains the allowed top-level keys and omits empty optional
fields. JSON uses sorted keys, UTF-8, compact separators and no added whitespace.
`envelope_hash` is SHA-256 of the canonical body; exported helper hash fields are
not themselves part of that body. The contract requires canonical text, so pretty
printed JSON, duplicate keys and extra top-level keys are rejected. The submitted
package and versions must match the envelope. Both sides carry pins. Deduplication
is scoped to a policy, requester and the update identity plus both integrity pins.
Changing an author note does not create a fresh attestation for the same update
for that requester. Another reviewer can independently submit it. The
original evidence is retained for judging and challenges.

| Level | Meaning | Consequence |
|---|---|---|
| 1 | Both tarballs were fetched and byte integrity verified by the client builder. | Six classes are eligible, but incomplete required evidence still blocks. |
| 2 | Checksums and dependency graph recovered from documented sources; no tarball bytes. | Only `MAINTAINER_SHIFT` and `DEP_ADDED` are eligible, with sufficient metadata. |
| 3 | Nothing usable can be pinned. | No judgment; `INCONCLUSIVE`. |

A recovered lockfile does not supply source code or authentic publisher history.
The builder fails without writing a new envelope when fetching or integrity
verification fails. Explicitly incomplete EGRESS or OPAQUE coverage, unsupported
evidence levels,
and malformed consensus output block a pass. For other missing or truncated
context, the model must mark its response inconclusive; this assessment depends
on consensus judgment.

The contract limits evidence to 12,288 UTF-8 bytes and challenge quotes to 1,024
UTF-8 bytes. Package names are capped at 128 characters and versions at 64. A
policy accepts at most 24 licence entries and `min_rounds` from 1 to the number
of blocking classes.

The client bounds downloads to 64 MiB and expanded file content to 128 MiB. File
lists are capped at 400 entries, candidate collections at 12, and source excerpts
at 1,200 bytes. Egress extraction examines changed source lines for explicit network patterns and records
its coverage. Encoded or dynamic calls may evade those patterns. Inspect coverage
rather than treating a missing candidate as a whole-program proof.

## Contract flow and ABI

Writes:

| Method | Purpose |
|---|---|
| `register_policy(allowed_licenses, blocking, min_rounds, min_level, challenge_bond)` | Create a policy; attached value funds its pool. Returns policy ID. |
| `fund_policy(policy_id)` | Add attached value to a pool. |
| `request_attestation(policy_id, package, from_version, to_version, level, envelope_hash, evidence)` | Validate and judge one envelope; store evidence and findings. Returns attestation ID. |
| `challenge(att_id, claimed_class, quote)` | Stake attached value on a missed blocking class in the stored evidence. Returns challenge ID. |
| `withdraw()` | Transfer the sender's credited balance. |

Views include `gate(att_id)`, `get_policy(policy_id)`, `report(policy_id)`,
`get_challenge(challenge_id)`, `attestation_count()`, `balance_of(who)` and
`solvency()`.

Each readable blocking class asks its own question using
`gl.eq_principle.prompt_comparative`. Evidence is fenced and embedded directions
are treated as material to judge. Initial risk locators must belong to a
class-specific identifier set: `license`, `publisher`, `install_hooks`,
`opaque_candidates`, `egress`, or `dependencies`, respectively. `DEP_ADDED` also
permits names of added dependencies; `OPAQUE`/`EGRESS` permit paths present in
their candidate rows. Arbitrary prose, JSON fragments and unlisted identifiers
are rejected. The locator must occur in the evidence, fit 128 characters and
contain neither `,` nor `@`; otherwise the judgment becomes inconclusive.
This restriction applies to initial class findings; challenge quotes retain
their separate verbatim-fragment rules.

The aggregate result is `CLEAN`, a risk class,
or `INCONCLUSIVE`. Unreadable required classes or an unmet round/level threshold
make the aggregate inconclusive even when other findings exist. The state records
findings, inconclusive classes, evidence level, envelope hash and judgment count. `registry_verification` records `VERIFIED`, a concrete
metadata-fetch/mismatch diagnostic, or `NOT_APPLICABLE` for other evidence levels.
`report()` counts aggregate verdicts; its class counts are not a count of every
individual finding.

## Challenge and accounting

A challenge claims a missing class already blocked by the policy. Its quote must
occur verbatim in the stored evidence. A quote absent from that evidence loses
its bond without a consensus round. Two differently framed referee judgments
must agree to uphold an admissible challenge. Another version or external material
is not a challenge to this attestation.

An upheld challenge adds a finding and changes the attestation's verdict; the
challenger's bond becomes a withdrawable credit. It does not earn an additional
bounty. A rejected bond remains in the policy pool. Credits do not reduce escrow
until `withdraw()` transfers value. `solvency()` checks
`sum(policy pools) + credited == escrowed`. Counters use `u32`; monetary values
use `u256`.

## CI and frontend

| `gate()` result | CLI exit | Meaning |
|---|---:|---|
| `CLEAN` | 0 | The recorded policy and evidence permit this update. |
| `RISK` | 1 | A blocking class was confirmed. |
| `INCONCLUSIVE` | 2 | The gate cannot establish a pass. |

Transport errors, malformed responses, missing or mismatched identity, and pending
or failed transactions must fail closed with exit 2. Consumers must pin the
network, contract, policy and update; accepting an unrelated clean attestation is
not a gate. A challenge may change a previous result, so consumers read current
state rather than treating a saved receipt as permanent approval.

The production interface must call the live contract and display the transaction
lifecycle, confirmed attestation and current gate. A historical table or local
fixture is evidence of a baseline, not a contract interaction. Deployment and
receipt badges can change only after confirmed writes and independently readable
state exist.

## Measurement and release criteria

The historical four-class mechanical baseline is preserved in
[`FINDINGS.md`](../FINDINGS.md). It is not a consensus benchmark. Repeat precisely
the same 45 package/version pairs under a published policy, keep transaction
failures and inconclusive results, and publish receipts alongside evidence hashes.
Declare whether the comparison uses four or six classes. Calculate differences
from confirmed outcomes; do not interpret unfinished rows as clean. Both risk and
inconclusive outcomes block CI, so report their combined fraction as the block
rate. A lower risk fraction alone does not establish fewer CI blocks.

Before claiming a live release, confirm Bradbury deployment, a registered policy,
a first real update attestation, readable `gate()` state, and a hosted frontend
that interacts with the contract. Publish the contract address, source revision,
policy hash and transaction receipts. Include actual consensus corpus coverage;
missing runs remain a documented release limitation. No simulated verdict should
be labelled live.

After every contract edit run `python3 test/run_tests.py`, rebuild the deployment
artifact, and run `ATTAINT_CONTRACT_PATH=contracts/attaint.bradbury.py python3
test/run_tests.py`. The local scripted
stub checks deterministic state and accounting; it does not simulate GenLayer
consensus or prove deployment compatibility. Live transaction verification remains
necessary. Secrets and private signing keys never belong in source, static assets,
receipts or a submission archive.
